2️⃣ UML 클래스 간의 관계 (Relationships)

선 모양(실선/점선)과 화살표 모양(빈 화살표/마름모 등)을 정확히 암기해야 합니다.

연관 관계 (Association) 실선 + 화살표

사람 (Person)
차 (Car)

2개 이상의 사물이 서로 관련되어 있는 상태. (사람이 차를 '소유'함)

의존 관계 (Dependency) 점선 + 화살표

고객 (Customer)
영수증 (Receipt)

한 사물의 명세가 바뀌면 다른 사물에 영향을 줌. 보통 '일시적인 사용' 관계 (고객이 물건을 살 때만 영수증 발생)

일반화 관계 (Generalization) 실선 + 빈 삼각형

고양이 (Cat)
동물 (Animal)

객체지향의 **상속(Inheritance)**. 'is a' 관계. 하위 사물이 상위 사물을 가리킴.

실체화 관계 (Realization) 점선 + 빈 삼각형

비행기 (Airplane)
«interface»
날 수 있는 (Flyable)

사물이 할 수 있거나 해야 하는 기능(인터페이스)을 그룹으로 묶어 실제로 구현하는 관계.

집합 관계 (Aggregation) 실선 + 빈 마름모

모니터 (Monitor)
컴퓨터 (Computer)

전체(컴퓨터)와 부분(모니터)의 관계. 독립적이라 컴퓨터가 없어져도 모니터는 남아있음.

합성 관계 (Composition) 실선 + 꽉 찬 마름모

엔진 (Engine)
자동차 (Car)

집합보다 강한 결합. 전체가 소멸하면 부분도 소멸. (자동차가 폐차되면 엔진도 끝)

3️⃣ 파이프-필터 아키텍처 (Pipe-Filter)

데이터 스트림 절차의 각 단계를 필터(Filter)로 캡슐화하고 파이프(Pipe)로 연결하는 구조입니다.

📥 Data In
Filter 1
데이터 전처리
Filter 2
데이터 변환
Filter 3
결과 추출
📤 Data Out
특징: 재사용성이 좋고, 확장이 쉽습니다. UNIX의 파이프라인(|)이 가장 대표적인 예시입니다.
단점으로는 데이터 변환 오버헤드가 발생할 수 있습니다.

📱 MVC 아키텍처

사용자 인터페이스와 비즈니스 로직을 분리하여 서로 영향 없이 개발할 수 있는 구조입니다.

  • M (Model): 데이터와 비즈니스 로직 처리
  • V (View): 사용자에게 보여지는 UI 화면
  • C (Controller): Model과 View 사이의 제어(라우팅) 담당

🥞 계층형 (Layered) 아키텍처

시스템을 계층으로 나누어 구성하며, 하위 계층은 상위 계층에 서비스를 제공합니다. (예: OSI 7계층)

프레젠테이션 계층 (UI)
비즈니스 로직 계층
데이터 접근 계층 (DB)

HIPO (Hierarchy IPO)

하향식 소프트웨어 개발을 위한 문서화 도구입니다.

가시적 도표 (Visual Table of Contents)
총체적 도표 (Overview Diagram)
세부적 도표 (Detail Diagram)
입력(Input) - 처리(Process) - 출력(Output)의 기능을 표현하며, 시스템의 분석 및 설계, 문서화에 사용됩니다.

N-S Chart (나시-슈나이더만 차트)

논리의 기술에 중점을 둔 도형식 표현 방법 (박스 다이어그램)

초기화 (Initialize)

GOTO문을 사용할 수 없으며, 순차, 선택, 다중 선택, 반복 등의 제어 논리 구조를 도형으로 표현합니다.

4️⃣ 요구사항 명세 & 소프트웨어 설계 원리

요구사항을 어떻게 기록할 것인가(명세)와, 좋은 소프트웨어를 만들기 위한 4가지 설계 원칙 및 모듈화 평가 기준(결합도/응집도)입니다.

📐

정형 명세 기법 (Formal)

  • ▪ 기반: 수학적 원리, 논리, 기호
  • ▪ 장점: 요구사항을 정확하고 간결하게 표현 가능, 결과의 일관성 보장, 모호성 없음.
  • ▪ 단점: 기호를 알아야 하므로 작성과 이해가 어려움. (사용자와의 의사소통에 불리)
대표 기법/도구 Z-스키마, Petri-Nets, VDM, CSP
📝

비정형 명세 기법 (Informal)

  • ▪ 기반: 자연어(일반 텍스트), 다이어그램(그림)
  • ▪ 장점: 특별한 기호를 배우지 않아도 되므로 사용자와 개발자 간의 의사소통이 매우 쉬움.
  • ▪ 단점: 자연어의 특성상 내용이 모호해질 수 있고, 작성자에 따라 일관성이 떨어질 수 있음.
대표 기법/도구 Use Case (유스케이스), FSM (상태 기계), 결정표

🧠 소프트웨어 설계의 4가지 기본 원리

1. 추상화 (Abstraction)

복잡한 문제에서 핵심적이고 공통적인 속성만 추출하여 단순화하는 기법.
종류: 과정, 데이터, 제어 추상화

2. 정보 은닉 (Info Hiding)

모듈 내부에 포함된 절차나 자료 구조를 숨겨서, 다른 모듈이 접근하거나 변경하지 못하게 하는 기법. (결합도 감소 목적)

3. 단계적 분해

하향식 설계(Top-Down) 전략으로, 큰 문제를 점차적으로 구체화하고 쪼개어 작은 문제로 분할하는 기법.

4. 모듈화 (Modularity)

소프트웨어를 독립적인 기능을 수행하는 '모듈'로 나누는 것. 시스템의 성능 최적화와 유지보수에 직결됨.

🔗 모듈화의 평가 기준: 결합도와 응집도 (필수 출제!)

좋은 소프트웨어 설계는 "결합도는 약하게, 응집도는 강하게(결약응강)" 만드는 것입니다.

5️⃣ 소프트웨어 개발 방법론 & CASE

소프트웨어를 어떻게 만들 것인가(방법론)와, 그것을 돕는 자동화 도구(CASE)입니다.

🔄 주요 개발 방법론

  • 폭포수 (Waterfall) 모델 이전 단계로 돌아갈 수 없다는 전제 하에 각 단계를 확실히 매듭짓고 다음 단계로 넘어가는 고전적 방법론.
  • 애자일 (Agile) 방법론 변화에 유연하게 대응하며 일정한 주기(Sprint)로 끊임없이 프로토타입을 만들어내는 가볍고 빠른 방법론. (스크럼, XP 등)
  • 나선형 (Spiral) 모델 (보엠 제안) 계획 ➔ 위험 분석 ➔ 개발 ➔ 평가를 나선형으로 반복하며 위험을 최소화하는 대규모 프로젝트용 모델.

🛠️ CASE 도구 (Computer-Aided Software Engineering)

소프트웨어 개발 과정의 일부 또는 전체를 자동화하여 개발 생산성과 품질을 높이는 도구입니다.

상위(Upper) CASE 개발 전반부(요구분석, 설계) 지원. 모델링, UI 설계 등을 돕습니다.
하위(Lower) CASE 개발 후반부(코드 작성, 테스트, 문서화) 지원. 소스 코드 생성 등을 돕습니다.
통합(Integral) CASE 소프트웨어 생명주기 전체 과정을 연결하고 자동화하는 도구.

6️⃣ 디자인 패턴, 프레임워크 & 컴포넌트

효율적인 재사용과 유지보수를 위한 3가지 핵심 요소입니다.

프레임워크 (Framework)

소프트웨어 개발을 수월하게 하기 위한 소프트웨어 환경(뼈대)입니다.

핵심 특징 (IoC): 제어의 역전. 개발자가 짠 코드를 프레임워크가 주도적으로 호출하고 제어합니다. (예: Spring, Django)

컴포넌트 (Component)

독립적인 기능을 수행하는 소프트웨어 모듈입니다. (레고 블록 조립과 유사)

핵심 특징: 내부 구현은 캡슐화되어 숨겨져 있으며, 외부와는 '인터페이스(Interface)'를 통해서만 통신하여 부품을 쉽게 교체할 수 있습니다.

자주 발생하는 문제를 해결하는 검증된 설계 템플릿

객체의 생성 과정을 캡슐화합니다.

  • 빌더 (Builder)
  • 팩토리 메서드 (Factory Method)
  • 프로토타입 (Prototype)
  • 싱글톤 (Singleton)
추·빌·팩·프·싱
구조 패턴 (7개)

클래스나 객체를 조합해 더 큰 구조를 만듭니다.

  • 어댑터 (Adapter)
  • 브리지 (Bridge)
  • 컴포지트 (Composite)
  • 데코레이터 (Decorator)
  • 퍼사드 (Facade)
  • 플라이웨이트 (Flyweight)
  • 프록시 (Proxy)
어·브·컴·데·퍼·플·프
행위 패턴 (11개)

객체 간의 상호작용과 책임 분배를 정의합니다.

템플릿 메서드, 옵저버, 상태(State), 전략(Strategy), 커맨드(Command), 책임 연쇄, 메멘토, 방문자(Visitor), 중재자(Mediator), 반복자(Iterator), 인터프리터
💡 출제 포인트: 옵저버(상태 변화 알림), 전략(알고리즘 교체), 상태(상태에 따른 행위 변화) 패턴이 객관식 설명으로 가장 많이 출제됩니다.
