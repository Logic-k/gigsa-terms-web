소프트웨어 테스트 & 품질
핵심 마스터보드

가장 헷갈리는 화이트/블랙박스, 상향/하향식 통합 테스트, 그리고 형상 관리와 국제 표준까지 한 방에 정리합니다.

1️⃣ 테스트 기법: 화이트박스 vs 블랙박스

내부를 볼 것인가(구조/코드), 외부만 볼 것인가(기능/명세). 기출 1순위 파트입니다.

화이트박스 테스트

White-Box Testing (구조적 테스트)

🔎

모듈의 내부 소스 코드 구조를 들여다보고, 논리적인 모든 경로(Path)를 테스트하는 기법입니다. (개발자 관점)

주요 종류 (기출 필수 암기)
  • ✓ 기초 경로 검사 (Base Path) McCabe의 순환 복잡도(V(G) = E - N + 2)를 이용해 독립적 경로 확인
  • ✓ 제어 구조 검사 조건 검사(Condition), 루프 검사(Loop), 데이터 흐름 검사(Data Flow)

블랙박스 테스트

Black-Box Testing (기능 테스트)

📦

내부 코드는 안 봅니다! 프로그램의 요구사항 명세서를 보며 기능이 제대로 작동하는지 확인하는 기법입니다. (사용자 관점)

주요 종류 (기출 필수 암기)
  • ✓ 동치 분할 (Equivalence Partitioning) 타당한 값과 타당하지 않은 값을 그룹으로 나눠 대표값 테스트
  • ✓ 경계값 분석 (Boundary Value Analysis) 오류는 주로 경계에서 발생! 경계값을 콕 집어 테스트 (가장 많이 출제)
  • ✓ 원인-결과 그래프 / 오류 예측 검사 입출력 관계 분석 / 테스터의 경험과 직관에 의존
💡

정적 분석 도구 vs 동적 분석 도구

정적 분석(Static): 프로그램을 실행하지 않고 소스 코드를 보며 결함(코딩 표준, 논리적 오류)을 찾아내는 방법입니다. (리뷰, 워크스루, 인스펙션)
동적 분석(Dynamic): 프로그램을 직접 실행하여 오류를 찾는 방법입니다. (화이트박스, 블랙박스 테스트 모두 동적 분석에 속함)

🔍 검증(Verification) vs 확인(Validation)

소프트웨어 테스트의 두 가지 핵심 관점 (V-모델)

  • 검증 (Verification) - "과정" 중심 "제품을 올바르게 만들고 있는가?"
    개발자 시각에서 요구사항 명세서대로 기능이 버그 없이 잘 구현되었는지 테스트합니다.     수행: 단위 테스트, 통합 테스트, 시스템 테스트
  • 확인 (Validation) - "결과" 중심 "올바른 제품을 만들고 있는가?"
    사용자 시각에서 실제 고객이 원했던 요구와 목적에 부합하는지 최종적으로 테스트합니다.     수행: 인수 테스트 (알파/베타 테스트)

🎮 인수 테스트: 알파(Alpha) vs 베타(Beta)

  • 알파(Alpha) 검사
    사용자가 개발자 환경(회사)에서 통제된 상태로 수행하는 검사.
  • 베타(Beta) 검사
    선정된 다수의 사용자가 실제 사용 환경에서 수행하는 검사. (필드 테스팅)

3️⃣ 형상 관리(Configuration Mgt) & 버전 관리

형상 관리 총정리 핵심: 베이스라인(Baseline)과 CCB

베이스라인 (기준선): 개발 과정의 특정 단계가 끝났을 때, 공식적으로 승인된 형상 항목들의 상태입니다. 기준선이 설정되면 이후의 변경은 반드시 공식적인 통제 절차를 거쳐야 합니다.
CCB (형상통제위원회, Configuration Control Board): 베이스라인 설정 이후 발생한 변경 요청(Change Request)을 검토하고 승인 혹은 거절하는 공식 기구입니다.

소프트웨어 버전 관리 도구 3가지 방식

공유 폴더 방식

매일 개발 완료된 파일을 로컬 PC의 공유 폴더에 복사하는 원시적인 방식.

대표 도구: SCCS, RCS

클라이언트/서버 방식

중앙 서버에 하나의 저장소를 두고, 여러 클라이언트가 동기화하는 방식.

대표 도구: CVS, SVN (Subversion)

분산 저장소 방식

원격 서버뿐만 아니라 각 개발자 PC에도 전체 저장소를 가지는 방식. (가장 최신)

대표 도구: Git, Bitbucket

4️⃣ SW 품질 표준 & CMMI 모델

소프트웨어의 품질을 평가하는 국제 표준(ISO)과 프로세스 성숙도 평가 모델(CMMI)입니다.

🌐 ISO/IEC 소프트웨어 품질 표준

ISO 9126

소프트웨어 품질 특성 평가 표준

6가지 품질 특성 암기: 기·신·사·효·유·이 (기능성, 신뢰성, 사용성, 효율성, 유지보수성, 이식성)

ISO 14598

소프트웨어 품질 평가 프로세스 표준

평가자, 개발자, 구매자 관점에서 품질 평가 과정을 정의

ISO 12119

패키지 소프트웨어 품질 요구사항

상용으로 판매되는 패키지 SW(COTS)에 대한 품질 테스트 표준

ISO 25000

SQuaRE (통합 표준)

기존의 ISO 9126, 14598 등을 통합한 차세대 소프트웨어 품질 평가 통합 프레임워크

🔄 소프트웨어 프로세스 관련 개발 표준

ISO/IEC 12207

소프트웨어 생명주기 프로세스 표준

소프트웨어 개발, 운영, 유지보수 등 전 과정의 프로세스를 분류한 국제 표준. (기본, 지원, 조직 생명주기 프로세스로 구성)

SPICE (ISO/IEC 15504)

소프트웨어 프로세스 평가를 위한 국제 표준

프로세스 수행 능력을 6단계로 평가: 불완전 ➔ 수행 ➔ 관리 ➔ 확립 ➔ 예측 ➔ 최적화 (CMMI와 유사)

CMMI 성숙도 레벨

능력 성숙도 통합 모델. 레벨 1부터 5까지 순서대로 외우세요.

1
초기 (Initial) 프로세스가 불안정하고 예측 불가
2
관리 (Managed) 프로젝트 단위의 프로세스 관리
3
정의 (Defined) 조직 차원의 표준화된 프로세스
4
정량적 관리 (Quantitatively Managed) 정량적(수치화된) 통계적 프로세스 통제
5
최적화 (Optimizing) 지속적인 프로세스 개선 및 혁신

5️⃣ 테스트 도구 & 소프트웨어 유지보수

자동화된 테스트 지원 도구들과 소프트웨어 개발 생명주기의 마지막 단계인 유지보수 유형입니다.

🛠️ 테스트 자동화 및 성능 점검 도구

🔍 정적 분석 도구

프로그램을 실행하지 않고 소스 코드의 코딩 표준, 복잡도, 결함을 분석합니다.

종류: pmd, cppcheck, SonarQube

⚡ 테스트 실행 도구

스크립트를 실행하여 테스트를 자동화합니다. (데이터 주도 방식 / 키워드 주도 방식)

종류: Selenium, Watir

📈 성능 점검 (부하) 도구

가상의 사용자(Virtual User)를 대량으로 생성하여 시스템의 처리량, 응답시간, 병목현상을 테스트합니다.

종류: JMeter, LoadRunner, 성능 부하 테스트

🧰 테스트 하네스 도구

테스트를 지원하기 위해 생성된 코드 및 데이터를 말합니다.

구성: 드라이버(Driver), 스텁(Stub), 목(Mock) 객체

소프트웨어 유지보수 (Maintenance) 4대 유형

교정형 (하자 보수)

Corrective Maintenance

개발 중 발견하지 못한 오류(버그)를 찾아 고치는 작업입니다.

적응형 (환경 적응)

Adaptive Maintenance

운영체제 업그레이드, 하드웨어 변경 등 새로운 환경에 소프트웨어를 맞추는 작업입니다.

빈도 1위!

완전형 (기능 개선)

Perfective Maintenance

본래 기능에 새로운 기능을 추가하거나 성능을 향상시키는 작업으로, 가장 많은 비용과 노력이 소요됩니다.

예방형 (예방 조치)

Preventive Maintenance

미래에 발생할지 모르는 오류를 대비하여 미리 코드를 재구성(리팩토링)하거나 구조를 개선하는 작업입니다.

📚 SW 공학의 주요 법칙 (보너스 암기)

브룩스의 법칙 (Brooks's Law)

"지연되고 있는 소프트웨어 프로젝트에 새로운 인력을 추가하면 프로젝트는 더욱 지연된다." (새로운 인력의 교육 시간 및 소통 비용 발생 때문)

보엠 (Boehm)

나선형(Spiral) 모델의 제안자. 소프트웨어 개발의 '위험 분석'을 가장 중요시함. (계획수립 ➔ 위험분석 ➔ 개발/검증 ➔ 고객평가)

정보처리기사 완벽 대비 가이드 2편 - 소프트웨어 테스트, 품질 및 형상 관리
